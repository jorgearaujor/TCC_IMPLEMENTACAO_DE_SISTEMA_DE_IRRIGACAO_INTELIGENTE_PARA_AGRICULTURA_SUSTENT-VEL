Na camada de percepção estão os sensores, os atuadores e o ESP32, cujo firmware lê os sensores, decide quando irrigar e aciona o relé. A camada de nuvem reúne o backend, isto é, a parte do sistema executada no servidor, implementada como uma API em Spring Boot que aplica as regras do sistema, e os serviços do Firebase, que armazenam os dados e autenticam os usuários. A camada de aplicação corresponde ao frontend, o painel web em Angular por meio do qual o usuário acompanha o sistema e envia seus comandos. Essas três camadas trocam dados pela rede Wi-Fi do local e pela internet, com mensagens HTTPS no padrão REST.

Os dados circulam em dois sentidos. No sentido do campo para o painel, o ESP32 envia as leituras, o seu estado e o registro de cada irrigação à API, que os grava no Firestore, e o painel consulta a API periodicamente para exibir os dados atualizados. No sentido inverso, cada ação do usuário no painel, como trocar o modo ou iniciar uma irrigação, é enviada à API, que a transforma em um comando e o entrega ao ESP32 na próxima consulta do dispositivo. Assim, o dispositivo nunca recebe conexões de fora, pois é sempre ele quem inicia a comunicação, o que dispensa configurar a rede local para aceitar acessos externos.

O código foi dividido em três aplicações independentes, uma para cada camada. O firmware separa a leitura dos sensores, o acionamento dos atuadores, as regras de irrigação e a comunicação. A API separa controladores, serviços, repositórios, modelos e segurança. O painel separa os serviços e os modelos compartilhados das telas. Essa divisão atende ao requisito de manutenibilidade (RNF12) e permite alterar uma parte sem modificar as demais.

\subsection{Comunicação entre as camadas}
\label{sec:rede}
\label{sec:longpolling}

No modelo de \citeonline{morchid2024}, a rede é uma camada própria, responsável por transportar os dados entre a percepção e a nuvem. Na arquitetura proposta neste trabalho, porém, ela não foi implementada como uma camada independente, com equipamentos ou software próprios. A comunicação é feita apenas por protocolos, usados pelas demais camadas para trocar dados entre si. O ESP32 conecta-se ao roteador Wi-Fi do local como uma estação comum e volta a se conectar automaticamente se a conexão cair (RNF09), e tanto o dispositivo quanto o painel se comunicam com a API pela internet, usando o protocolo HTTPS, que protege as mensagens com o protocolo TLS (RNF03). As mensagens seguem o estilo REST, com os dados representados em JSON (RNF15). Por isso, a Figura~\ref{fig:arquitetura} representa a comunicação pelas setas que ligam as camadas, identificadas pelo rótulo Comunicação, e não como uma camada separada.

Cada informação enviada pelo dispositivo é uma requisição HTTP com um documento JSON no corpo. O Quadro~\ref{lst:json-telemetria} mostra, como exemplo, a mensagem de telemetria que o ESP32 envia a cada 10 segundos à rota \texttt{/api/webhooks/telemetry}.

O principal desafio da comunicação foi entregar comandos a um dispositivo que está atrás da rede local do usuário e, portanto, não pode receber conexões vindas da internet. A solução adotada foi o long-polling \cite{rfc6202}, técnica em que o ESP32 faz uma requisição à rota de comandos e a API só responde quando há um comando para ele ou quando se passam 30 segundos sem comandos. No segundo caso, a API devolve o código 204, que indica que a requisição foi atendida, mas não há conteúdo a entregar. Em seguida, o dispositivo abre uma nova requisição. Com isso, um comando chega ao dispositivo quase imediatamente quando há uma consulta aberta, e em no máximo cerca de 30 segundos no pior caso (RNF06), sem que o ESP32 precise consultar a API a todo instante. A implementação desse mecanismo na API é apresentada na Subseção~\ref{subsec:dispatch}.

\section{Camada de percepção}
\label{sec:percepcao}

A camada de percepção corresponde ao dispositivo de campo. Ela é uma única camada, formada por duas partes que funcionam juntas, o hardware, que coleta os dados do ambiente e age sobre ele, e o firmware, o programa gravado no ESP32 que controla esse hardware. Esta seção discute primeiro o hardware, com os componentes e as suas ligações, e depois o firmware, com a sua organização, o seu funcionamento e os cálculos que ele realiza para decidir quanto irrigar.

\subsection{Firmware do dispositivo de campo}
\label{sec:firmware}

O firmware foi escrito em C++ com o framework Arduino para o ESP32, usando as bibliotecas DHT sensor library, LiquidCrystal\_I2C e ArduinoJson. Ele preserva a lógica de cálculo do primeiro protótipo e a organiza em módulos com responsabilidades separadas. A classe \texttt{IrrigationState} guarda o estado do dispositivo (modo, autorização, volume de água, temperaturas mínima e máxima, irrigação em andamento e latitude) e os parâmetros agronômicos, reunidos na estrutura \texttt{ConfigIrrigacao}. O módulo \texttt{IrrigationService} concentra as regras de irrigação, o \texttt{IrrigationRunner} controla o relé durante uma irrigação, o \texttt{CommandPoller} recebe os comandos da API e o \texttt{ApiClient} faz todas as chamadas HTTP. Os módulos \texttt{SoilSensor}, \texttt{DhtSensor}, \texttt{Relay} e \texttt{Display} encapsulam o acesso ao hardware.

Ao ser ligado, o dispositivo mantém o relé desligado, conecta-se ao Wi-Fi, sincroniza o relógio por NTP no fuso de Brasília e busca na API a sua configuração inicial, com o modo, a autorização, a latitude e os parâmetros agronômicos. Se a API não responder, o firmware segue com valores padrão locais, conforme a regra RN22. A partir daí, o trabalho é dividido entre tarefas concorrentes do FreeRTOS, sistema operacional de tempo real usado pelo ESP32 \cite{barry2016freertos}. Três tarefas ficam ativas o tempo todo. A \texttt{sensorTask} lê os sensores e envia os dados, a \texttt{statusSyncTask} envia o estado do dispositivo e a \texttt{commandPollTask} aguarda os comandos da API. Uma quarta tarefa, a \texttt{irrigationTask}, é criada no início de cada irrigação e encerrada ao fim dela, o que garante que só exista uma irrigação por vez. Como as tarefas leem e alteram o mesmo estado, o acesso a ele é protegido por um mutex, que impede que duas tarefas o modifiquem ao mesmo tempo (RNF08).

A \texttt{sensorTask} lê os sensores a cada 10 segundos, atualiza as temperaturas mínima e máxima registradas desde que o dispositivo foi ligado, mostra os valores no display e envia a telemetria à API. A cada 20 segundos, a \texttt{statusSyncTask} envia o estado completo do dispositivo. Quando um envio falha, o módulo \texttt{ApiClient} repete a tentativa com intervalos crescentes, até cinco vezes. Esgotadas as tentativas, a leitura é descartada para não travar a tarefa (RNF07). A Figura~\ref{fig:fluxograma} resume o ciclo de funcionamento e a decisão de irrigar.

\subsubsection{Leitura da umidade do solo}

O conversor analógico-digital do ESP32 tem 12 bits e entrega valores entre 0 e 4095. Para reduzir o ruído, o firmware faz 16 leituras seguidas, converte cada uma em tensão e usa a média, em volts. No sensor resistivo, quanto mais úmido o solo, menor a tensão de saída. Por isso, a umidade percentual é obtida por interpolação linear entre duas tensões de calibração, uma com o sensor seco e outra com o sensor imerso em água, conforme a Equação~\ref{eq:umidade}:
 
\begin{equation}
  U = \frac{L_{seco} - L}{L_{seco} - L_{sat}} \times 100
  \label{eq:umidade}
\end{equation}

\noindent em que:
\begin{itemize}
  \item $U$ é a umidade do solo (\%);
  \item $L$ é a tensão média lida no sensor no momento da leitura (V);
  \item $L_{seco}$ é a tensão de calibração com o sensor seco, que corresponde a 0\% de umidade (V);
  \item $L_{sat}$ é a tensão de calibração com o sensor imerso em água, que corresponde a 100\% de umidade (V).
\end{itemize}

O resultado é limitado ao intervalo de 0 a 100\%. No firmware, as tensões de calibração estão configuradas em 2,8~V e 1,2~V, respectivamente, e devem ser ajustadas após a montagem, medindo-se a tensão de saída do sensor seco e imerso em água. O Quadro~\ref{lst:umidade} mostra a aplicação da Equação~\ref{eq:umidade} no firmware.

\vspace{0.6\baselineskip}
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=C++, caption={Cálculo da umidade do solo no firmware (trecho de SoilSensor)}, label={lst:umidade}]
#define SOIL_MAX_VOLTAGE 2.800f
#define SOIL_MIN_VOLTAGE 1.200f

bool readSoilPercent(float &outValue) {
  float tensao = lerTensaoMedia();
  float umidade = ((SOIL_MAX_VOLTAGE - tensao) /
      (SOIL_MAX_VOLTAGE - SOIL_MIN_VOLTAGE)) * 100.0f;
  outValue = constrain(umidade, 0.0f, 100.0f);
  return true;
}
\end{lstlisting}
\vspace{-0.5\baselineskip}
\fonte{Elaborado pelo autor}
\end{minipage}
\medskip

Nas linhas 1 e 2, as constantes \texttt{SOIL\_\allowbreak MAX\_\allowbreak VOLTAGE} e \texttt{SOIL\_\allowbreak MIN\_\allowbreak VOLTAGE} definem os valores de $L_{seco}$ e $L_{sat}$. A função \texttt{readSoilPercent}, declarada na linha 4, recebe por referência a variável em que o resultado será gravado. Na linha 5, a função \texttt{lerTensaoMedia} devolve a tensão $L$, já calculada como a média das 16 leituras. As linhas 6 e 7 aplicam a Equação~\ref{eq:umidade}, e a linha 8 usa a função \texttt{constrain} para limitar o resultado ao intervalo de 0 a 100\%. \subsubsection{Cálculo da irrigação}
\label{subsec:calculo}

No modo automático, o volume de água segue o método FAO-56, com a ET$_0$ estimada pela equação de Hargreaves-Samani (Equação~\ref{eq:hargreaves}) a partir das temperaturas mínima e máxima registradas pelo dispositivo e da latitude informada no painel \cite{allen1998,hargreaves1985}. O primeiro passo é calcular a radiação extraterrestre $R_a$, que depende apenas da latitude e do dia do ano, pelas Equações~\ref{eq:ra} a~\ref{eq:omega} \cite{allen1998}:

\begin{equation}
  R_a = \frac{24 \cdot 60}{\pi}\, G_{sc}\, d_r \left[\omega_s \sin\varphi \sin\delta + \cos\varphi \cos\delta \sin\omega_s\right]
  \label{eq:ra}
\end{equation}

\begin{equation}
  d_r = 1 + 0{,}033 \cos\!\left(\frac{2\pi}{365} J\right)
  \label{eq:dr}
\end{equation}

\begin{equation}
  \delta = 0{,}409 \sin\!\left(\frac{2\pi}{365} J - 1{,}39\right)
  \label{eq:delta}
\end{equation}

\begin{equation}
  \omega_s = \arccos\left(-\tan\varphi \tan\delta\right)
  \label{eq:omega}
\end{equation}

\noindent em que:
\begin{itemize}
  \item $R_a$ é a radiação extraterrestre (MJ\,m$^{-2}$\,dia$^{-1}$);
  \item $G_{sc}$ é a constante solar, igual a 0,0820~MJ\,m$^{-2}$\,min$^{-1}$;
  \item $d_r$ é a distância relativa inversa entre a Terra e o Sol;
  \item $\delta$ é a declinação solar (rad);
  \item $\omega_s$ é o ângulo horário do pôr do sol (rad);
  \item $\varphi$ é a latitude (rad), negativa no hemisfério sul;
  \item $J$ é o número do dia no ano, de 1 a 365 ou 366.
\end{itemize}

Para uso na Equação~\ref{eq:hargreaves}, $R_a$ é convertida para lâmina equivalente de evaporação, em mm\,dia$^{-1}$, multiplicando-se o valor por 0,408 \cite{allen1998}. O dia do ano $J$ é obtido do relógio sincronizado por NTP, e as temperaturas mínima e máxima são as registradas pelo DHT11 desde que o dispositivo foi ligado, e não apenas no dia corrente, ponto que é retomado nos trabalhos futuros. O Quadro~\ref{lst:eto} mostra a função \texttt{calcularEto}, que realiza esses cálculos.

\vspace{0.6\baselineskip}
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=C++, caption={Cálculo da ET$_0$ pela equação de Hargreaves-Samani no firmware (função calcularEto)}, label={lst:eto}]
float calcularEto(float tempMin, float tempMax,
                  float latitude, int diaDoAno) {
  float tempMed = (tempMin + tempMax) / 2.0f;
  float latRad = latitude * (float)M_PI / 180.0f;

  float dr = 1.0f + 0.033f *
      cosf(2.0f * (float)M_PI / 365.0f * diaDoAno);
  float delta = 0.409f * sinf(
      (2.0f * (float)M_PI / 365.0f * diaDoAno) - 1.39f);
  float cosOmegaS = -tanf(latRad) * tanf(delta);
  cosOmegaS = std::max(-1.0f, std::min(1.0f, cosOmegaS));
  float omegaS = acosf(cosOmegaS);

  const float Gsc = 0.0820f;
  float raMj = (24.0f * 60.0f / (float)M_PI) * Gsc * dr *
      (omegaS * sinf(latRad) * sinf(delta) +
       cosf(latRad) * cosf(delta) * sinf(omegaS));
  float raMm = raMj * 0.408f;

  const float C = 0.0023f;
  float td = std::max(0.0f, tempMax - tempMin);
  return C * raMm * sqrtf(td) * (tempMed + 17.8f);
}
\end{lstlisting}

\end{minipage}

A função recebe, nas linhas 1 e 2, as temperaturas mínima e máxima, a latitude em graus e o dia do ano. A linha 3 calcula a temperatura média $T_{med}$, e a linha 4 converte a latitude $\varphi$ para radianos. As linhas 6 e 7 calculam a distância relativa inversa entre a Terra e o Sol, $d_r$, pela Equação~\ref{eq:dr}, e as linhas 8 e 9 calculam a declinação solar $\delta$, pela Equação~\ref{eq:delta}. As linhas 10 a 12 calculam o ângulo horário do pôr do sol $\omega_s$, pela Equação~\ref{eq:omega}, e a linha 11 limita o argumento do arco-cosseno ao intervalo de $-1$ a 1, o que evita erro numérico em latitudes extremas. As linhas 14 a 17 calculam a radiação extraterrestre $R_a$, em MJ\,m$^{-2}$\,dia$^{-1}$, pela Equação~\ref{eq:ra}, com a constante solar $G_{sc}$ definida na linha 14, e a linha 18 converte o resultado para mm\,dia$^{-1}$. Por fim, as linhas 20 a 22 aplicam a equação de Hargreaves-Samani (Equação~\ref{eq:hargreaves}). A linha 21 garante que a amplitude térmica $T_{max} - T_{min}$ nunca seja negativa, o que evita a raiz quadrada de um número negativo, e a linha 22 devolve a ET$_0$ em mm\,dia$^{-1}$.

Com a ET$_0$ calculada, a evapotranspiração da cultura é obtida pela Equação~\ref{eq:etc}, com o K$_c$ correspondente à cultura e à fase escolhidas no painel. A ET$_c$, em milímetros por dia, é então convertida em volume por planta. Como 1~mm de água sobre 1~m$^2$ equivale a 1~L, basta multiplicá-la pela área ocupada por planta, dada pelos espaçamentos entre plantas e entre linhas, conforme a Equação~\ref{eq:volume-planta}:

\begin{equation}
  A_p = E_p \cdot E_l
  \qquad\qquad
  V_p = ET_c \cdot A_p
  \label{eq:volume-planta}
\end{equation}

\noindent em que:
\begin{itemize}
  \item $A_p$ é a área ocupada por planta (m$^2$);
  \item $E_p$ é o espaçamento entre plantas na linha (m);
  \item $E_l$ é o espaçamento entre linhas (m);
  \item $V_p$ é o volume de água por planta (L);
  \item $ET_c$ é a evapotranspiração da cultura (mm\,dia$^{-1}$), dada pela Equação~\ref{eq:etc}.
\end{itemize}

O tempo de irrigação depende da vazão disponível por planta, que é a vazão de cada gotejador multiplicada pelo número de gotejadores por planta. Como todas as plantas são irrigadas ao mesmo tempo pela mesma válvula, o tempo de abertura, em segundos, e o volume total aplicado são dados pela Equação~\ref{eq:tempo}:

\begin{equation}
  t = \frac{V_p}{q_g \cdot n_g} \cdot 3600
  \qquad\qquad
  V_t = V_p \cdot N
  \label{eq:tempo}
\end{equation}

\noindent em que:
\begin{itemize}
  \item $t$ é o tempo de abertura da válvula (s);
  \item $V_p$ é o volume de água por planta (L), dado pela Equação~\ref{eq:volume-planta};
  \item $q_g$ é a vazão de cada gotejador (L\,h$^{-1}$);
  \item $n_g$ é o número de gotejadores por planta;
  \item 3600 é o fator de conversão de horas para segundos;
  \item $V_t$ é o volume total aplicado (L);
  \item $N$ é o número total de plantas.
\end{itemize}

O Quadro~\ref{lst:irrigacao} mostra a função \texttt{calcularIrrigacao}, que aplica as Equações~\ref{eq:etc}, \ref{eq:volume-planta} e~\ref{eq:tempo} a partir da ET$_0$ e dos parâmetros configurados no painel, e a linha do modo automático que calcula o volume total.

\vspace{0.6\baselineskip}
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=C++, caption={Cálculo do volume e do tempo de irrigação no firmware (função calcularIrrigacao)}, label={lst:irrigacao}]
IrrigationResult calcularIrrigacao(float etoMm, float kc,
    float espacamentoPlantasM, float espacamentoLinhasM,
    float vazaoGotejadorLph, int numGotejadoresPlanta) {
  float etcMmDia = etoMm * kc;
  float areaPorPlantaM2 =
      espacamentoPlantasM * espacamentoLinhasM;
  float volumeLitrosPorPlanta = etcMmDia * areaPorPlantaM2;
  float vazaoTotalPorPlantaLph =
      vazaoGotejadorLph * numGotejadoresPlanta;

  if (vazaoTotalPorPlantaLph == 0.0f) {
    return {0.0f, 0.0f};
  }

  float tempoIrrigacaoHoras =
      volumeLitrosPorPlanta / vazaoTotalPorPlantaLph;
  float tempoIrrigacaoSegundos =
      tempoIrrigacaoHoras * 3600.0f;
  return {tempoIrrigacaoSegundos, volumeLitrosPorPlanta};
}

\subsubsection{Modos de operação e comandos}

A irrigação automática só começa quando as quatro condições a seguir são verdadeiras ao mesmo tempo:
\begin{itemize}
    \item o modo de operação é o automático;
    \item o usuário autorizou a irrigação automática;
    \item a umidade do solo está abaixo do limiar configurado;
    \item não há outra irrigação em andamento (RN01).
\end{itemize}

A autorização vem desativada por padrão e funciona como uma trava de segurança contra acionamentos indesejados (RN02). No modo manual, o usuário informa no painel o volume total de água, em litros, e o dispositivo calcula o tempo de abertura com a mesma vazão total das plantas, conforme a Equação~\ref{eq:tempo-manual}:

\begin{equation}
  t = \frac{V_t}{q_g \cdot n_g \cdot N} \cdot 3600
  \label{eq:tempo-manual}
\end{equation}

\noindent em que $V_t$ é o volume total informado pelo usuário (L), e $t$, $q_g$, $n_g$ e $N$ têm o mesmo significado da Equação~\ref{eq:tempo}.

O comando de iniciar só é aceito com o dispositivo em modo manual e sem irrigação em andamento (RN03), e o comando de interromper desliga o relé e registra o tempo real decorrido (RN05). O Quadro~\ref{lst:manual} mostra o trecho da função \texttt{executarModoManual} que calcula o tempo de irrigação.

\section{Camada de nuvem}
\label{sec:backend}

A camada de nuvem reúne o processamento e o armazenamento que ficam fora do dispositivo e do navegador do usuário. Neste sistema, ela é formada pelo backend e pelos serviços do Firebase, e por isso a camada de nuvem e o backend são tratados juntos nesta seção. O backend é a parte do sistema executada no servidor e responsável pelas regras de negócio, como validar os comandos, aplicar as permissões de cada perfil e decidir o que gravar no banco de dados. Ele foi implementado como uma API REST, ou seja, as suas funções são oferecidas aos outros componentes por meio das rotas HTTP apresentadas na Tabela~\ref{tab:endpoints}. Assim, a API é a forma como o backend se comunica com o dispositivo e com o painel. Os dados são guardados no Cloud Firestore, e a autenticação dos usuários é feita pelo Firebase Authentication.

A API foi desenvolvida em Java 17 com o framework Spring Boot \cite{springboot2026}. O acesso ao Firestore e ao Firebase Authentication é feito pelo Firebase Admin SDK, a documentação das rotas é gerada automaticamente pela biblioteca springdoc-openapi, que publica uma interface Swagger, e a aplicação pode ser empacotada em uma imagem Docker, o que permite executá-la da mesma forma em qualquer máquina (RNF14).

\subsection{Organização interna da API}

Internamente, é comum organizar uma API REST em camadas de código, cada uma com uma responsabilidade. Essas camadas internas não se confundem com as camadas da arquitetura da Figura~\ref{fig:arquitetura}, pois todas elas fazem parte do backend e, portanto, da camada de nuvem. A camada de controladores recebe as requisições HTTP e devolve as respostas. A camada de serviços aplica as regras de negócio. A camada de repositórios lê e grava os dados no banco. Os modelos e os objetos de transferência de dados descrevem as informações que circulam entre essas camadas. Essa separação permite alterar uma camada sem afetar as outras, como trocar o banco de dados modificando apenas os repositórios. \subsection{Implementação do long-polling}
\label{subsec:dispatch}

Na API, a entrega de comandos descrita na Subseção~\ref{sec:longpolling} é implementada pela classe \texttt{CommandDispatchService}, apresentada no Quadro~\ref{lst:dispatch}. Ela guarda, para cada dispositivo, duas filas em memória. A fila \texttt{waiters} contém as consultas do dispositivo que estão abertas, à espera de um comando, e a fila \texttt{pending} contém os comandos que ainda não foram entregues.

\vspace{0.6\baselineskip}
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java, caption={Entrega de comandos por long-polling (trecho de CommandDispatchService)}, label={lst:dispatch}]
public void enqueue(String deviceId, Command command) {
    var queue = waiters.get(deviceId);
    if (queue != null) {
        CompletableFuture<Optional<Command>> waiting;
        while ((waiting = queue.poll()) != null) {
            if (waiting.complete(Optional.of(command))) {
                return;
            }
        }
    }
    pending.computeIfAbsent(deviceId, id -> new ConcurrentLinkedQueue<>())
        .add(command);
}

public CompletableFuture<Optional<Command>> poll(String deviceId, long timeoutMillis) {
    var pendingQueue = pending.get(deviceId);
    Command alreadyPending = (pendingQueue == null) ? null : pendingQueue.poll();
    if (alreadyPending != null) {
        return CompletableFuture.completedFuture(Optional.of(alreadyPending));
    }
    var future = new CompletableFuture<Optional<Command>>();
    var queue = waiters.computeIfAbsent(deviceId, id -> new ConcurrentLinkedQueue<>());
    queue.add(future);
    timeoutExecutor.schedule(() -> {
        if (future.complete(Optional.empty())) {
            queue.remove(future);
        }
    }, timeoutMillis, TimeUnit.MILLISECONDS);
    return future;
}
\end{lstlisting}
\vspace{-0.5\baselineskip}
\fonte{Elaborado pelo autor}
\end{minipage}
\medskip

O método \texttt{enqueue}, nas linhas 1 a 13, é chamado quando o painel gera um comando. A linha 2 obtém as consultas abertas do dispositivo, e as linhas 3 a 10 percorrem essa fila. Se houver uma consulta aberta, a linha 6 a completa com o comando, que é devolvido imediatamente ao ESP32 como resposta, e a linha 7 encerra o método. Se não houver nenhuma consulta aberta, as linhas 11 e 12 guardam o comando na fila \texttt{pending}, para que seja entregue na próxima consulta.

O método \texttt{poll}, nas linhas 15 a 30, é chamado quando o dispositivo consulta a rota de comandos. As linhas 16 a 20 verificam se já existe um comando pendente e, se houver, devolvem-no imediatamente. Caso contrário, as linhas 21 a 23 criam uma resposta futura, do tipo \texttt{CompletableFuture}, e a registram na fila \texttt{waiters}, deixando a consulta à espera. As linhas 24 a 28 agendam o fim do prazo. Se nenhum comando chegar dentro do tempo definido, de 30 segundos, a linha 25 completa a resposta vazia, que o controlador converte no código 204, e a linha 26 remove a consulta da fila. Do lado do controlador, a resposta é devolvida de forma assíncrona com a classe \texttt{DeferredResult} do Spring, o que libera a thread do servidor enquanto o dispositivo aguarda.

\subsection{Segurança e autenticação}
\label{subsec:seguranca}

A API usa dois mecanismos de autenticação, um para cada cliente, configurados com o Spring Security. O dispositivo envia em todas as requisições uma chave fixa no cabeçalho HTTP \texttt{X-Device-Key}, conferida pelo filtro \texttt{DeviceKeyFilter}, apresentado no Quadro~\ref{lst:devicekey}. A chave é lida de uma variável de ambiente e nunca aparece no código-fonte da API (RNF03).

\medskip

A linha 1 obtém o endereço da rota pedida, e as linhas 2 a 5 verificam se ela pertence ao dispositivo. Se a rota for do painel, o filtro a deixa seguir sem verificar a chave, já que ela será tratada pelo filtro do Firebase. Para as rotas do dispositivo, a linha 6 lê o cabeçalho \texttt{X-Device-Key}, e as linhas 7 a 11 comparam o valor recebido com a chave configurada. As linhas 1 e 2 retiram o prefixo \texttt{Bearer} do cabeçalho e validam o token com o Firebase Admin SDK, que confirma que ele foi emitido pelo Firebase e ainda não expirou. As linhas 3 e 4 procuram o usuário na coleção \texttt{usuarios}, que funciona como lista de acesso. Se ele não estiver cadastrado, as linhas 5 a 9 recusam a requisição com o código HTTP 403, que indica que a credencial é válida, mas não dá acesso ao sistema, mesmo que a pessoa tenha uma conta no Firebase. Por fim, as linhas 10 a 12 definem o papel do usuário a partir do campo \texttt{tipo} do cadastro. O Administrador/Operador recebe o papel \texttt{ROLE\_ADMIN}, e os demais recebem o papel \texttt{ROLE\_USER}.

As rotas que alteram o sistema são marcadas com a anotação \texttt{@PreAuthorize}, configurada para exigir o papel de administrador por meio da expressão \texttt{hasRole('ADMIN')}, de modo que a restrição de escrita ao perfil Administrador/Operador (RN19) é verificada na própria API, e não apenas escondida no painel. A autenticação do painel pode ser desligada pela variável de ambiente \texttt{DASHBOARD\_\allowbreak AUTH\_\allowbreak ENABLED}, recurso usado durante o desenvolvimento para testar as telas sem login. % CONFERIR: deixar DASHBOARD_AUTH_ENABLED=true na versão avaliada

\section{Camada de aplicação}
\label{sec:frontend}

A camada de aplicação é a parte do sistema com a qual o usuário interage. Neste trabalho, ela corresponde ao frontend, o painel web por meio do qual o Administrador/Operador e o Visualizador acompanham as leituras dos sensores, consultam o histórico e, no caso do Administrador/Operador, controlam a irrigação e configuram o sistema. O painel não acessa o dispositivo nem o banco de dados diretamente, pois todas as informações passam pela API.

O painel foi desenvolvido em Angular 21 \cite{angular2026}, com componentes independentes (standalone) e signals, valores reativos que atualizam automaticamente as partes da tela que dependem deles. A estilização usa o Tailwind CSS, os gráficos usam o Chart.js e o login usa o SDK JavaScript do Firebase.

A pasta \texttt{core} reúne o que é compartilhado entre as telas. Em \texttt{models} ficam as definições dos dados recebidos da API, em \texttt{services} os serviços que acessam a API e o Firebase, em \texttt{guards} as regras que protegem as rotas do painel, em \texttt{interceptors} os interceptadores que atuam sobre as requisições e em \texttt{mocks} os dados simulados usados quando o painel funciona sem a API (RNF11). O serviço \texttt{IrrigationService} concentra a comunicação com a API. Ele consulta o estado do dispositivo a cada 5 segundos e as leituras dos sensores a cada 10 segundos (RNF05) e guarda os resultados em signals, de modo que todas as telas exibem os mesmos dados sem fazer requisições repetidas. Após uma ação do usuário, como iniciar uma irrigação, o serviço antecipa a próxima consulta para que a tela reflita a mudança logo em seguida.

O acesso às telas é controlado por dois guards. O \texttt{authGuard} exige que o usuário esteja autenticado, e o \texttt{adminGuard} libera as telas de cadastro de usuários e de culturas apenas para o Administrador/Operador. Dois interceptadores atuam em todas as requisições à API. export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (!req.url.startsWith(environment.apiBaseUrl)) {
    return next(req);
  }

  return from(auth.getIdToken()).pipe(
    switchMap((token) => {

        ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
        : req;

  );
